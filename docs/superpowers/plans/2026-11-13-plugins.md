# Chat UI in the package, with plugins — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the chat UI from a copied 600-line template into `dopus/react`, make tool lines, approval cards and
file attachments opt-in plugins from `dopus/plugins`, and leave the app a ~20-line wrapper plus one sectioned CSS file.

**Architecture:** The server entry (`dopus`) learns two request-body inputs: the client's capabilities
(`dopus.approvals`, which hides `confirm` tools when false) and `data-dopus-file` parts (validated, shown to the model
as server-written text). Two new client entries, built with a `'use client'` banner, hold the shell (`AgentChat`,
`AgentWidget`) and the plugins; the shell routes message parts to plugins in array order. The `ui/agent-chat.tsx`
template becomes the thin wrapper, so the existing `dopus update` history mechanism migrates untouched 0.2.x copies.

**Tech Stack:** TypeScript 6, React 19.3, Next.js 16.4, AI SDK `ai@7.0.166` + `@ai-sdk/react@4.0.170`, tsdown 0.23,
vitest 5, Playwright 1.64, Biome.

**Spec:** `docs/superpowers/specs/2026-11-13-plugins-design.md`

## Global Constraints

- Server entry `dopus` (`src/index.ts`, `src/cli.ts`) must not import React, `next/navigation` or any client entry.
- Client entries `dopus/react` and `dopus/plugins`: built files start with `'use client'`.
- Optional peer dependencies (`peerDependenciesMeta.<name>.optional: true`): `react ^19`, `react-dom ^19`,
  `@ai-sdk/react ^4`, `next ^16`, `react-markdown ^10`, `remark-gfm ^4`. `ai` and `zod` stay required peers.
- All class names start with `dopus-`; every class the package renders is defined in `templates/ui/agent-chat.css`.
- Request body field: `dopus: { approvals: true }` (shell sends `dopus: { approvals: <bool> }` always).
- File part type `data-dopus-file`, data `{ id, name, type, size }`; server limits: `id` string 1–200 chars, `name`
  string ≤ 255, `type` string ≤ 100, `size` finite number ≥ 0, at most 10 file parts per message; violations → 400
  `Invalid file attachment`.
- Client attachment defaults: `maxFiles` 5, `maxSize` 20 MB (20 * 1024 * 1024 bytes).
- Model-facing file text (server-written):
  `The user attached a file: <JSON name> (<type or "unknown type">, <size> bytes), fileId <JSON id>. Read it with a tool that takes the fileId; you cannot see its contents otherwise.`
  where `<JSON x>` is `JSON.stringify(x)`.
- Plugins are created once (module scope or `useMemo`), like `channel` and `history`.
- Existing behaviour and browser tests (14 in `test/ui`, 5 in `test/ui-db`) must keep passing.
- Version 0.3.0 (bumped at release, not in these tasks). No publish in this plan.
- The example app builds against `packages/dopus/dist`: run `pnpm --filter dopus build` before `pnpm example:build`.

## Review Focus

1. A message with attached files and no text: Send is enabled and the message goes out with only file parts
   (Task 6 test `sends files without text`).
2. Enter pressed while an upload is still running: nothing is sent until the upload finishes or is removed (Task 6
   test `does not send while uploading`).
3. A restored conversation (history, other tab) containing `data-dopus-file` parts in an app without the
   attachments plugin: the shell shows read-only file chips, no crash (Task 4 test `renders sent file parts without
   the plugin`).
4. A file name with quotes, newlines or 255 characters: the model text stays one well-formed line (Task 2 test
   `quotes names safely`).
5. A wrapper that creates `plugins` inline on every render: the conversation, transport and channel subscription are
   not reset, and the capability sent is the current one (Task 4 test `reads plugins at send time`).

```ts
export type ChatPart = UIMessage['parts'][number]
export interface ChatContext {
  messages: UIMessage[]
  labels: AgentChatLabels
  busy: boolean
  /** Approval ids of open cards in the newest message. */
  openApprovals: string[]
  respondToApproval: (approvalId: string, approved: boolean) => void
}
export interface PartContext extends ChatContext {
  message: UIMessage
  /** The message is not the newest one. */
  stale: boolean
  /** Jobs this chat started that have not reported back. */
  waitingJobs: ReadonlySet<string>
}
export interface ComposerContext extends ChatContext {
  /** Report this plugin's draft state: content lets Send go out without text; blocked holds Send back. */
  setDraftState: (state: { hasContent?: boolean; blocked?: boolean }) => void
}
export interface Draft { text: string; parts: ChatPart[] }
export interface ChatPlugin {
  name: string
  capabilities?: { approvals?: boolean }
  renderPart?: (part: ChatPart, ctx: PartContext) => ReactNode | undefined
  renderFooter?: (ctx: ChatContext) => ReactNode
  renderComposer?: (ctx: ComposerContext) => ReactNode
  /** Return the draft to send (may add parts), or false to hold it back. */
  beforeSend?: (draft: Draft) => Draft | false | Promise<Draft | false>
  /** Called after a message went out, so the plugin can clear its draft. */
  afterSend?: () => void
}
export function definePlugin(plugin: ChatPlugin): ChatPlugin
export function renderPluginPart(plugins: readonly ChatPlugin[], part: ChatPart, ctx: PartContext): ReactNode | undefined
export function clientFeatures(plugins: readonly ChatPlugin[]): { approvals: boolean }
```
